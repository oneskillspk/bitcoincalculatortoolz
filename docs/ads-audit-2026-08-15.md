# Site-wide Ads / Placement Audit — 15 Aug 2026

Method: headless Chromium sweep of 26 routes (EN + TR, home, hubs, 18 calculators, 2 learn
articles) at 3 breakpoints (1440, 1280, 1024, 390), consent granted, with two behaviour
profiles: (a) fast visit + calculate + scroll-to-bottom, (b) 14 s idle dwell + slow staged
scroll. Measured per route: `[data-slot=A|B|C|D]` mount count, painted count, rendered
height, `[data-affiliate-placement]` zones painted vs hidden, horizontal overflow, console
placement warnings.

## Findings (severity ordered)

### P0-1 — Slot A renders as a full-height block, not a 728x90 anchor
`/calculators/dca` desktop: Slot A paints at **831 px** tall; `/calculators/capital-gains-tax`
at 193 px; mobile DCA 262 px. Contract is 100 px desktop / 60 px mobile (`SlotA_PreCalcAnchor`
reserves exactly that via `minHeight`). `forceFormat="image-banner"` is honoured
(`data-affiliate-format="image-banner"`), so the creative itself is scaling to container width
with no aspect cap. Consequence: a ~700 px unreserved expansion above the calculator = severe
CLS on the site's highest-traffic page, and the fold is pushed below the input form.

### P0-2 — Three calculators have zero post-result monetization
`/calculators/capital-gains-tax`, `/calculators/hodl-strategy`, `/calculators/lump-sum-vs-dca`
mount Slot A and Slot C only; **Slot B count = 0, Slot D count = 0** at every breakpoint, both
behaviour profiles. Only the generic pre-footer band paints (1 surface vs 5–6 on healthy
routes). These are transaction-intent pages — the highest EPC moment on the site is unsold.

### P1-1 — Slot C never reaches `armed`
Slot C mounts on 20 routes but painted on exactly **one** (`/calculators/bitcoin-savings`).
Probe on DCA/CGT after 14 s: `aria-hidden=false`, orchestrator `visible=true`, computed
`opacity: 0` → the component's own IO gate (threshold 0.25 + 2 s dwell) never satisfies.
Slot C sits at y≈7 482 px (DCA) inside a 110 px reserved box; at 0.25 threshold on a fast or
staged scroll it never accumulates the dwell. Net: one of four inventory units is dark
site-wide.

### P1-2 — Desktop density cap silently drops Slot C
On `/calculators/power-law` and `/calculators/bitcoin-lot-size` all four slots arm; the cap
(`maxSlots = 3` desktop) demotes C. Correct behaviour, but combined with P1-1 it means C's
real fill rate is ~5%. The cap should be evaluated against *painted* slots, not armed ones.

### P2-1 — Learn articles carry a permanently hidden surface
`/learn/how-to-calculate-bitcoin-lot-size` and `/learn/bitcoin-millionaire-calculator-guide`:
6 affiliate surfaces mounted, 5 painted, 1 never painted at any breakpoint or scroll position.

### P2-2 — TR homepage under-monetized
`/tr/` paints a single `inline` surface; EN `/` paints 8. The TR calculator mirror
(`/tr/hesaplayicilar/bitcoin-dca-hesaplayicisi`) is at full parity (6), so this is homepage-only.

### P2-3 — `/tools` has one surface only
Pre-footer band only, no slot system mounted.

### Clean
No duplicate slot claims anywhere (post-`slotClaim` fix holds), no horizontal overflow on any
promo card or slot at 1440/1280/1024/390, no console errors beyond one transient upstream 429
on the price proxy, no legal/utility page carries ads (correct).

## Action plan

**Phase 1 — stop the bleeding (P0)**
1. Cap Slot A's creative box: hard `max-height` of 100 px desktop / 60 px mobile with
   `object-fit: contain` on the banner image, and make the reserved `minHeight` match the
   rendered height so CLS is zero. Verify DCA desktop returns ≤100 px.
2. Wire `<sz.SlotB />` and `<sz.SlotD />` into the CGT, HODL-strategy and lump-sum-vs-DCA
   result flows, matching the DCA pattern (`hasResultSignal` from the calculator's result state).

**Phase 2 — recover dark inventory (P1)**
3. Relax Slot C's arm gate: threshold 0.25 → 0.01 with `rootMargin: "200px 0px"` and dwell
   2 s → 800 ms, so a normal reading scroll arms it.
4. Move the density cap after the paint decision (count only slots that actually rendered a
   creative), so an unarmed C no longer consumes a slot budget it never uses.

**Phase 3 — coverage parity (P2)**
5. Diagnose and fix the one hidden surface on the two learn articles.
6. Bring `/tr/` to EN homepage parity (Bybit grid mirror with TR copy).
7. Decide whether `/tools` should carry the slot system or stay editorial-only.

**Verification gate for every phase**
Re-run the two-profile sweep across all 26 routes and assert: Slot A ≤100/60 px, Slot B painted
on 100% of result-emitting calculators, Slot C painted on ≥60% of long-form routes, zero
duplicate claims, zero horizontal overflow, no new console warnings.
